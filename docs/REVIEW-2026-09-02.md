# Code review — firmware/dial-idf, branch firmware/somnus-port, 2026-09-02

Read-only targeted review. Scope, in priority order: (1) the uncommitted
timezone setup-gate diff, (2) every pad write path, (3) the recurring-bug check
over every persisted setting and every `CMD_*`, (4) the 16-deep command queue.
Out of scope: LVGL layout, `dial_pad_discovery` internals, `dial_ota`, style,
structure. No refactors proposed; where a finding has an obvious one-line
remedy it is named, nothing more.

All paths are relative to `firmware/dial-idf/` unless they start with `docs/`.

## 0. Understanding (stated before the findings)

### nav_policy phase-to-screen routing (`main/main.c:151-409`)

Evaluated on the LVGL task from `dispatch_tick` whenever the store generation
or the power level changes, with the *current* screen as the default `arg`.
Precedence, top to bottom:

1. OTA takeover: `ota.status` DOWNLOADING/READY_REBOOT forces `SCR_UPDATING`
   (unless unattended and the display is in standby); leaving that screen any
   other way lands on `SCR_UPDATE`.
2. Fresh-device welcome: `fresh_device && !welcomed` pins `SCR_WELCOME` during
   `PH_BOOT`/`PH_WIFI_CONNECTING`/`PH_WIFI_PORTAL`.
3. **New:** timezone setup gate — in `PH_READY`/`PH_DEGRADED`/
   `PH_SOMNUS_CONNECTING`/`PH_PAD_DISCOVERY`, if `!tz_prompted` and
   `dial_time_get_iana_tz()` returns false, force `SCR_TIMEZONE` with
   `arg = 1 + ui_zone`. This returns *before* the phase switch, so nothing in
   the switch (sticky sets included) is consulted while the gate is active.
4. Phase switch:
   - `PH_WIFI_PORTAL`: `SCR_PASSKEY` on a rejected join, else sticky
     NETPICK/PASSKEY, else `SCR_WIFI_PORTAL`.
   - `PH_READY`/`PH_DEGRADED`/`PH_WIFI_LOST`/`PH_SOMNUS_CONNECTING`/
     `PH_PAD_DISCOVERY`, with `have_state`: update-prompt override (scoped to
     the dial face), passive screens dismissed to `SCR_STANDBY` on idle, sticky
     set (MENU/WIFI/ABOUT/UPDATE/SETTINGS/BRIGHTNESS_MENU/ADJUST_MODE/
     PAD_ADDRESS/TIMEZONE) returns `cur`, fresh dual device → `SCR_SIDEPICK`,
     else `SCR_STANDBY` or `SCR_DIAL(ui_zone)`.
   - Same group, no `have_state`: sticky set (MENU/SETTINGS/ABOUT/WIFI/
     BRIGHTNESS/BRIGHTNESS_MENU/UPDATE/PAD_ADDRESS/TIMEZONE/ADJUST_MODE)
     returns `cur`; else `SCR_PAD_DISCOVERY`, `SCR_CONNECTING` (READY) or
     `SCR_ERROR`.
   - `default` (BOOT/WIFI_CONNECTING): `SCR_CONNECTING`, unconditionally, no
     stickiness.

### worker_task command handling (`main/main.c:859-1321`)

One task. Sequence: knob/haptics init → `dial_net_bringup()` (blocking) →
`dial_time_start()` (restores POSIX TZ + IANA name from NVS) → **initial pad
connect loop** (`:910-941`: re-reads `pad_url` per attempt, runs discovery on
failure, `PH_DEGRADED` + backoff otherwise; **never calls
`dial_cmd_receive`**) → seeds temp range, first poll, `PH_READY` → steady-state
loop. Only the steady-state loop drains the queue (`:973`): non-coalesced kinds
go straight to `handle_immediate_cmd` one at a time; `CMD_SET_TEMP`/
`CMD_TOGGLE_ON` bursts coalesce per zone into at most one power write plus one
temp write, stamped with `issued_us` so late acks cannot roll back newer input.
`CMD_TZ_CHANGED` is applied only here (`:847-852`). Polls are gated on 2.5 s of
input quiet and a due interval; `mut_device_state` keeps optimistic on/temp if
input arrived after the poll began and clears `ui_temp_dc` only on a
successful poll with no newer input.

### Assumptions I had to make

- The spec's "after the first successful connect" (`docs/SPEC-timezone-source.md:320`)
  means the **pad** connect, not Wi-Fi: it says "instead of the dial face",
  and the dial face only exists after the pad connects.
- Devices upgraded from the Orion-era `dial-v1.4.x` line share the NVS
  `"time"` namespace with this port (same repo, same partition layout). I did
  not verify the partition table across the two lines.
- `dial_net_bringup()` blocks until STA is connected. I read `dial_wifi.c` only
  around `root_get`/`save_post`.
- LVGL can deliver CLICKED/RELEASED to widgets of the outgoing screen during a
  load animation. Taken from `ui_router.c:60-70`'s own comment, not verified
  against LVGL 8.4.
- `dial_state_stamp_input()` inside `dial_cmd_post()` (`dial_state.c:703`) is
  intended, so every post counts as input for the poll gate and for
  `predates_input`.

## 1. Findings, ranked by severity

### F1 — HIGH — The gate fires in phases where its own command cannot be applied; the first-run zone pick can be silently lost

**Where:** `main/main.c:247-255` (phase list), `main/main.c:910-941` (connect
loop never drains), `components/dial_ui/scr_timezone.c:152-158`,
`docs/SPEC-timezone-source.md:320` and `:193-200`.

The gate lists `PH_SOMNUS_CONNECTING`, `PH_PAD_DISCOVERY` and `PH_DEGRADED`,
all of which are set inside the initial connect loop *before* the pad has ever
answered. `PH_SOMNUS_CONNECTING` is set at `:912`, immediately after Wi-Fi
comes up, so on every boot of a zone-less device the picker is raised at the
earliest possible moment — and that moment is precisely when `worker_task`
is not draining the queue. The spec says "after the first successful connect"
and the main.c comment at `:197-198` repeats it; the phase list does not
implement it.

Consequence chain on a fresh device (default pad address, no browser-supplied
zone, i.e. the `SCR_NETPICK` path this gate exists for):

1. Wi-Fi joins → `PH_SOMNUS_CONNECTING` → gate raises the picker.
2. User picks a zone: `HAPTIC_CONFIRM`, `tz_prompted = true`, `CMD_TZ_CHANGED`
   posted, screen leaves. To the user it is done.
3. The command sits in the RAM queue. Settings' Timezone row reads "Not set";
   the picker (if reopened) shows no checkmark. The gate will not re-raise
   (`tz_prompted`).
4. If the pad connects this boot (the common case, after discovery's up-to-58 s
   scan), the zone applies late but applies. If it does **not** — pad off,
   different subnet, discovery misses — the pick is lost at the next reboot
   with no indication, and the next boot raises the picker again as if the
   user had never answered.

The spec accepted this latency for a *deliberate* Settings visit while the pad
is unreachable (`:193-200`). The gate changes that: it makes the pre-connect
window the *default* first-run path for the pick, so the accepted gap is now
on the happy path, not an edge.

Two secondary effects of the same phase list:

- While the gate holds the screen during `PH_PAD_DISCOVERY`/`PH_DEGRADED`, the
  user cannot see `SCR_PAD_DISCOVERY`'s scan progress or `SCR_ERROR`'s retry
  countdown. Not a trap (dismissal works), but the picker hides the connection
  status for the whole duration.
- `go_back()` (`scr_timezone.c:108-110`) routes to `SCR_DIAL(zone)` with
  `have_state == false`; that face renders "--" for one dispatch tick until
  `nav_policy` replaces it (see F9).

**Smallest remedy consistent with the spec:** gate on `PH_READY` only (the
only phase set exclusively after `dial_somnus_connect()` succeeds, `:957`
and `:1233`). A steady-state `PH_DEGRADED` device returns to `PH_READY` on the
next good poll, so nothing is lost. Alternatively drain the queue inside the
connect loop, which is a larger change and out of this review's scope.

### F2 — MEDIUM — Devices upgraded from the Orion-era firmware have a valid clock but no IANA key, so the gate fires on every boot

**Where:** `components/dial_time/dial_time.c:64-78` (restore), `:147-151`
(getter); `main/main.c:251`; history: `git show dial-v1.4.2:firmware/dial-idf/components/dial_time/dial_time.c`
(persists `"posix_tz"` only, no IANA key) and `dial-v1.4.2:firmware/dial-idf/main/main.c:1192-1194`
(called `dial_time_set_iana_tz()` from the account's device timezone).

`"iana_tz"` was introduced in `69c1073` (2026-09-01). Every device that ran the
`dial-v1.4.x` line has `"time"/"posix_tz"` written and no `"iana_tz"`.
`restore_posix_tz()` applies the POSIX string (`s_tz_set = true`, clock
correct once SNTP lands) but leaves `s_iana_set = false`. The gate keys on
`s_iana_set`, so such a device is routed to the picker on every boot even
though its clock is right. One pick fixes it permanently; a user who swipes
it away instead is nagged each boot. The Settings row also reads "Not set"
on these devices (pre-existing from `69c1073`, not new to this diff).

Whether this matters depends on the assumption above about shared NVS. If the
owner's bench units were flashed over from `dial-v1.4.x`, they will show this
on the first boot of this build.

### F3 — MEDIUM (pre-existing) — CMD_WIFI_RESET, CMD_FACTORY_RESET, CMD_OTA_CHECK and CMD_OTA_APPLY are dead while the device is stuck in the initial connect loop

**Where:** `main/main.c:910-941` (no drain), `main/main.c:720-729`,
`components/dial_ui/scr_wifi.c:127-134`, `components/dial_ui/scr_settings.c:322-329`,
`components/dial_ui/scr_update.c:158-170`. Same shape at
`dial-v1.4.2:firmware/dial-idf/main/main.c:1832`, so this predates the port.

This is item 3(a) applied to the command set. The 2026-07-28 "never trap the
user" fix (`main.c:380-401`) makes Menu/Wi-Fi/Settings/Update reachable with
no device state, and its comment names "Settings' Re-link, Wi-Fi change, and
About's update — the only tools that FIX a stuck dial". The commands those
screens post are queued but not serviced until the pad connects, which for a
stuck dial is never:

- `scr_wifi.c:131` sets the button label to "Restarting..." and posts
  `CMD_WIFI_RESET`. Nothing restarts. The label stays.
- Factory reset: same, silently.
- "Check for updates": no "Checking..." (that is set by the worker), reads as
  a dead button. Beta toggle persists fine but the check never runs.

The pad-address change got a workaround (`f2a954b`, re-read inside the loop).
The others did not. `CMD_TZ_CHANGED` is the fifth member of this group and is
what F1 is about.

### F4 — LOW — Drop-oldest can evict CMD_PAD_SETTINGS_CHANGED or CMD_TZ_CHANGED, leaving persisted and applied state disagreeing until reboot

**Where:** `components/dial_state/dial_state.c:68` (16 deep), `:701-714`
(drop oldest); `components/dial_ui/scr_settings.c:309-320`;
`components/dial_somnus/dial_somnus.c:13` (5 s HTTP timeout).

All nine `CMD_*` kinds share the one queue. The worker can be blocked for up
to 5 s in a single pad request (a write to an unreachable pad, or the
`dial_somnus_connect()` probe run by a *previous* `CMD_PAD_SETTINGS_CHANGED`),
longer in `CMD_OTA_CHECK`. A knob spin posts one `CMD_SET_TEMP` per detent, so
16 newer commands inside that window is reachable by a fast spin.

Sequence: toggle Bed Mode (NVS written, command posted) → go to the dial face →
spin 16+ detents while the worker is still blocked → the Bed Mode command is
the oldest and is dropped. Result: `dial_state.pad_single_zone` (persisted,
shown by the Settings row) says One Bed; `dial_somnus`'s `s_single_zone_mode`
still says Dual, so side1 writes still go out and the next poll's
`zone_present[]` still reports dual. The dial face reads "LEFT SIDE"/"RIGHT
SIDE" while Settings reads "One Bed". Two screens disagree; nothing flags it.
Reboot heals it (`main.c:909`). Same mechanism for a dropped `pad_url` change
(steady-state polls keep using the old URL). A dropped `CMD_TZ_CHANGED` is at
least shown honestly as "Not set", but the user already got the confirm
haptic.

The drop-oldest bias is right for temp steps; it is only these three
carry-no-payload-or-carry-the-payload commands that lose state.

### F5 — LOW — The single-zone write guard returns true, so the worker commits a write the pad never received

**Where:** `components/dial_somnus/dial_somnus.c:215-222`,
`main/main.c:1012-1027` (commits on `true`), `main/main.c:446-447`
(`ui_zone` coercion happens only on a poll).

Window: user is on the ZONE_B face of a dual pad, flips Bed Mode to One Bed,
returns to the dial. Until the next successful poll (≥ 2.5 s quiet, plus the
worker's connect re-probe) the UI still shows face B. A knob turn or power tap
there posts a side1 command; `post_side_field` skips the network call and
returns `true`; `mut_zone_temp`/`mut_zone_on` commit as if applied and clear
the optimistic value, so the numeral and the power state show a value the pad
never got. The next poll overwrites `zones[B]` with side0's mirrored values
and coerces `ui_zone` to A. Self-corrects within one poll cycle; the "BOTH
SIDES" label appears only after that same poll.

The reverse mismatch (dial says Dual, pad is actually One Bed → side1 writes
are spec-undefined) is undetectable from the API and already accepted in
`dial_somnus.h:22-39` and `scr_dial.c:404-409`.

### F6 — LOW — pad_single_zone is captured once before the connect loop and applied after it

**Where:** `main/main.c:909` (capture), `:943` (apply), `:956` (first poll).

A Bed Mode change made during a long connect loop (reachable via Settings,
which is sticky there) is persisted but the loop applies the stale capture at
`:943`, so the first poll at `:956` classifies `present[]` with the old mode.
The queued `CMD_PAD_SETTINGS_CHANGED` is drained on the very first steady-state
iteration and re-applies it, forcing a fast re-poll. Self-heals in seconds
unless that command was evicted (F4). Re-reading `dial_state_get_zone_mode()`
at `:943` instead of using the pre-loop capture would close it; noted, not
proposed.

### F7 — LOW — Three comment inaccuracies in the new nav_policy block

**Where:** `main/main.c:229-233`, `:357-365`, `:197-198`.

- `:229-233` claims `PH_WIFI_LOST` "is only reachable after PH_READY was
  already hit once". `net_event_cb` (`:1349-1353`) sets it from `PH_DEGRADED`
  too, and the initial connect loop sets `PH_DEGRADED` at `:938`. So it *is*
  reachable pre-READY. Consequence is benign — the gate skips that window and
  fires on the next `PH_SOMNUS_CONNECTING` — but the stated reason is wrong.
- `:357-365` justifies adding `SCR_TIMEZONE` to the `have_state` sticky set as
  protecting "the gate-raised timezone picker" from a pad connect landing. The
  gate-raised picker never reaches that line: the gate returns at `:253`
  before the switch. What the sticky entry actually protects is the
  Settings-raised visit (`arg == 0`) from a routine poll. The change is still
  correct; the reason given is not.
- `:197-198` says "after the first successful connect"; the condition at
  `:247-248` fires before it (F1).

### F8 — LOW — The gate's arg tracks ui_zone, so the first poll can rebuild the picker mid-scroll

**Where:** `main/main.c:252`, `main/main.c:446-447`,
`components/dial_ui/ui_router.c:101-104` (different arg → rebuild),
`components/dial_ui/scr_timezone.c:204` (settles on row 1 at create).

If the persisted `ui_zone` is B and the pad reports single-zone, the first
poll coerces `ui_zone` to A. The gate then returns `SCR_TIMEZONE` with arg 1
instead of 2; `ui_router_go` treats that as a different screen and rebuilds
it, resetting the rotor to the first zone while the user may be scrolling.
Once per boot, only on that zone mismatch.

### F9 — LOW — Dismissing a pre-connect gate lands on a live dial face for one tick

**Where:** `components/dial_ui/scr_timezone.c:108-110`, `main/main.c:380-406`,
`components/dial_ui/scr_dial.c:688-706`.

With `have_state == false` (F1's phases), `go_back()` shows `SCR_DIAL(zone)`.
`on_state` early-returns so it renders "--", and the next `dispatch_tick`
(≤ 50 ms, the `set_tz_prompted` commit already bumped the generation)
replaces it with CONNECTING/ERROR/PAD_DISCOVERY. In that tick the power disc
is created and clickable; a tap posts `CMD_TOGGLE_ON` with `want_on = true`
(store zeroed), which the worker applies after the pad connects, possibly
minutes later. Practically unreachable by a human; listed for completeness.

Related, not a bug: a `DIAL_NET_EV_GOT_IP` while `have_state` is false sets
`PH_WIFI_CONNECTING` (`:1357`), whose `default` case yanks the picker to
`SCR_CONNECTING` without setting `tz_prompted`; the gate re-raises on the next
`PH_SOMNUS_CONNECTING`. The user is bounced, not trapped.

## 5. Item 4 — the 16-deep drop-oldest queue

**Who shares it:** every `CMD_*` above — the two hot kinds and the seven
rare ones — on one `xQueueCreate(16, …)` (`dial_state.c:68`). `dial_cmd_post`
(`:701-714`) drops the head on overflow and posts the newcomer; the newcomer is
never the one dropped.

**When it can overflow:** only while the worker is not draining. Steady state:
one blocked pad request (≤ 5 s) or one OTA check. Pre-connect: the whole
initial loop (F3), so any 17 posts during a long connect loop evict the
oldest — e.g. repeated Bed Mode taps plus a Wi-Fi reset plus a zone pick.

**Sequences that leave persisted and applied state disagreeing:**

1. `CMD_PAD_SETTINGS_CHANGED` evicted by 16 newer temp steps → Settings says
   One Bed / new URL; `dial_somnus` runs Dual / old URL until reboot. The
   dial face's side label follows the *applied* mode (via `zone_present`), the
   Settings row follows the *persisted* one, so the two screens contradict
   each other without any error surface (F4).
2. `CMD_TZ_CHANGED` evicted → the user got a confirm; the zone is not set;
   Settings honestly says "Not set", the gate does not re-raise this boot.
3. `CMD_TOGGLE_ON` evicted behind temp steps → temp written to an off side;
   face shows ON until the next poll reverts. Visible, self-healing.
4. `CMD_SET_TEMP` evicted → intended (newest wins).
5. `CMD_WIFI_RESET`/`CMD_FACTORY_RESET` evicted → nothing happens; the user
   sees no reboot and retries. No state divergence.
6. `CMD_OTA_*` evicted → no "Checking…" ever appears; no divergence.

Cases 1 and 2 are the only ones where the UI does not make the divergence
apparent as a divergence. Both need a blocked worker plus a burst; case 1 is
reachable by a deliberate sequence, case 2 mostly via the pre-connect loop.
